使用说明（已完成代码见本目录 server/、client/）

一、工程结构
  common\protocol.h   协议定义：ImgHead_t（16 字节头）、控制码、错误码、常量
  server 服务器：图像生成 + 监听 + 每客户端控制/发送线程
  client  PC 客户端：心跳 + 收图 + 断线重连

二、构建
  依赖：VS2019/2022（x64）+ CMake ≥ 3.13 + G:\库\libevent\dev 开发包。
  若开发包不在默认位置，用 -DLIBEVENT_DEV_DIR=路径 指定。
    cmake -B build -A x64
    cmake --build build --config Release

三、运行
 server.exe            服务器（监听 9995，最多 10 客户端，Ctrl+C 退出）
 client.exe            客户端（默认连 127.0.0.1:9995）
client.exe IP 端口    指定服务器地址
 client.exe -s         连接成功后自动开始收图（测试用）

  客户端按键：s=开始收图  q=停止收图  h=手动心跳  x=退出
  每 30 帧自动保存一帧图像到 frame_XXXX.raw（640*480 裸灰度，307200 字节）。

四、协议速览
  所有消息以 16 字节 ImgHead_t 开头：flag[4]="CAM0" + ctl_code + err_code + nDataLen。

  控制码：
    1  CTL_HEARTBEAT_REQ   客户端 -> 服务器：请求心跳
    2  CTL_HEARTBEAT_RESP  服务器 -> 客户端：心跳应答（后带 4 字节数据）
    3  CTL_REQ_IMAGE       客户端 -> 服务器：开始传输图像
    4  CTL_STOP_IMAGE      客户端 -> 服务器：停止传输图像
    5  CTL_IMG_DATA        服务器 -> 客户端：16 字节头 + 640x480 图像数据
    6  CTL_CTRL_DEV        客户端 -> 服务器：设备控制（当前应答"未支持"）

  错误码：0 正常 / 1 图像等待超时 / 2 服务器已满 / 3 未知控制码 / 4 设备控制未实现

五、超时与重连参数（common\protocol.h 中可调）
  图像生成间隔 100ms（10 帧/秒）
  发送线程等 img_ready 超时 5 秒（超时发 err_code=1 的空头）
  客户端心跳间隔 3 秒；读超时 3 秒
  断线/出错/超时后每 2 秒自动重连

六、实现要点
  · 服务器主线程 evconnlistener 监听；图像生成线程每 100ms 生成一帧并广播
    img_ready（Windows CONDITION_VARIABLE）；每客户端 1 个控制线程
    （独立 event_base + bufferevent）+ 1 个图像发送线程。
  · 线程安全：evthread_use_windows_threads()；每客户端发送加锁，保证
    "16 字节头 + 图像数据"不被打断；共享图像缓冲在锁内拷贝。
  · 客户端单线程事件循环 + 键盘输入线程（event_active 跨线程通知）；
    收包用"先收 16 字节头、再按 nDataLen 收载荷"的状态机。










整体架构

共同基础：一套 16 字节协议头（common/protocol.h）
结构：flag[4]="CAM0" + ctl_code + err_code + nDataLen，正好 16 字节
控制码：1 心跳请求 / 2 心跳应答 / 3 请求图像 / 4 停止图像 / 5 图像数据 / 6 设备控制
所有数据都按“先 16 字节头、再 nDataLen 字节载荷”的帧格式传输，这是 TCP 流式协议的标准做法，天然兼容粘包/半包
Server（server.c）：三类线程
图像生成线程（全局唯一）：高精度定时器每 20ms 生成一帧，写进全局缓冲并广播条件变量（server.c:443）
控制线程（每客户端一个）：解析请求、启停发送线程（server.c:309）
发送线程（每客户端一个）：等“新帧”信号后把最新一帧发出去（server.c:127）
Client（client.c）：单线程 + 状态机
所有网络、定时器、键盘动作都在同一个 event_base 里跑，天然线程安全
用 ST_* 状态机管理连接阶段：ST_DISCONNECTED → ST_CONNECTING → ST_IDLE → ST_WAIT_HB/ST_IMAGE
唯一的额外线程是键盘线程，因为 getchar() 阻塞，通过 event_active() 跨线程唤醒主循环（client.c:721）
Server 关键点讲解
生产者-消费者模型：g_img_lock + g_img_cond 把生成线程和各客户端的发送线程连起来。生成线程持锁写图、
递增帧序号，发送线程在锁上 SleepConditionVariableCS 等信号。用“帧序号”而不是“标志位”判断有没有新帧，避免丢帧/重复帧
跳帧策略：发送线程只 memcpy“最新一帧”，客户端跟不上就自然跳帧，保证延迟最低；网络发送在锁外进行，某个客户端慢不会卡住生成线程
每客户端独立 event loop：ctrl_thread_main 里每个客户端有自己的 event_base + bufferevent，互不阻塞；配合 evthread_use_windows_threads() 保证 libevent 内部线程安全
send_lock：保证“16 字节头 + 图像数据”这两次 bufferevent_write 之间不被同一客户端的其他发送插队
稳帧的关键：timeBeginPeriod(1) 把系统定时器精度提到 1ms，配合 CreateWaitableTimer 才能稳定 50fps
Client 关键点讲解
收图状态机（read_cb，client.c:128 之后的核心）：两阶段解析——先攒够 16 字节头，校验 CAM0 后调 on_header() 分发，再按 nDataLen 收载荷，收齐调 on_payload()。回调里用循环处理“一次到达多个包”
ST_IDLE 丢数据保护：read_cb 开头检查 ST_IDLE 时直接清空输入缓冲——这就是之前“按 q 后非法头标志刷屏、误重连”问题的根源（按 q 时残留半帧数据被当成了协议头）
心跳闭环：空闲每 3 秒发心跳 → ST_WAIT_HB → 应答后回 ST_IDLE 重新计时；3 秒没应答触发读超时 → 断线重连，链路断掉最多 3 秒就能发现
重连去重：g_reconnect_pending 防止断线事件重复触发连开多个定时器
GDI 预览：CreateDIBSection 拿到可直接写像素的内存，灰度展开成 24 位 RGB 后 BitBlt；窗口消息由 10ms 定时器泵，不用单独开 UI 线程
每个 client 独立保存目录：frames_时间_PID，多个客户端各存各的
